# Triggers cloud por polling

Implementación: `src/Core/TriggerProviders/CloudPollingProviders.php`. Prueba aislada: `php tests/triggers/cloud_polling.php`. Las lecturas usan HTTP simulado en las pruebas; no se registran suscripciones, no se solicita OAuth y no se procesa la cola real.

Los doce eventos de esta matriz están implementados y listos para configuración externa. Esto no implica que sus credenciales estén configuradas, que el proveedor conceda acceso o que el cron de una instalación esté activo. Los nodos de acción mantienen sus identificadores y comportamiento; el catálogo de triggers configura un inicio independiente.

## Credenciales y ejecución

Guardar una credencial `generic_bearer`; su campo API Key admite el access token plano, normalizado centralmente, o JSON como `{"access_token":"TOKEN_FICTICIO"}`. El trigger referencia el ID de la credencial. No guardar secretos en parámetros del workflow. Este adaptador requiere un token vigente, sin prefijo `Bearer`, para la API de destino. No implementa un flujo de consentimiento OAuth ni renueva access tokens. Habilitar las APIs de Google y consentir los scopes indicados con una identidad que ya tenga acceso al recurso. Configurar el intervalo de polling en el administrador y ejecutar el cron del proyecto cada minuto mediante PHP CLI.

Un access token Microsoft `application` requiere `token_mode=application` y `user_id` para correo o `drive_id` para OneDrive. `delegated` es el modo predeterminado; `/me` solo sirve con token delegado. La validación local impide usar `/me` en el modo application declarado; Microsoft valida los permisos y el tipo real del token. Una cadena OAuth válida no demuestra acceso al recurso.

Cada llamada `poll()` hace exactamente una petición GET, con página de hasta 100 elementos, timeout de conexión de 5 segundos, timeout total de 20 segundos, TLS verificado, redirecciones deshabilitadas y respuesta máxima de 4 MiB. No se realizan efectos remotos ni reintentos HTTP dentro de una llamada. `has_more=true` solicita otra pasada programada; los cursores se conservan tras reiniciar PHP. La infraestructura compartida reclama el trigger y guarda estado, eventos y trabajos de forma coordinada; el adaptador no accede directamente a la BD ni a la cola.

El estado se enlaza al tipo de trigger, configuración y token: cambiar cualquiera de ellos exige desactivar/reactivar y establecer una nueva línea base. La rotación manual del token también necesita esa nueva línea base. Los cursores y su vínculo no son datos del evento ni se exponen en la salida del workflow. Un token válido que caduque produce error de autenticación y requiere sustitución por el administrador.

El evento devuelve `id`, `type`, `occurred_at` cuando la API lo permite y `data`. La deduplicación duradera es por configuración receptora e ID del evento; el almacenamiento central coordina esa deduplicación con el encolado. La precisión temporal de corte es un segundo: se incluye la igualdad con `activated_at` para no perder eventos del segundo de activación. No existe garantía de una ejecución o un efecto externo exactamente una vez. Los cambios intermedios que el proveedor compacte entre lecturas no pueden reconstruirse.

## Reintentos, interrupciones y seguridad

- 429, 408, 5xx o fallo de conexión/lectura: `TriggerRetryException`; respeta `Retry-After` numérico o fecha HTTP mediante el reloj inyectado, limitado a 1–86.400 segundos (60 por defecto). Cuotas Google identificadas por `rateLimitExceeded`, `userRateLimitExceeded` o `quotaExceeded`: 300 segundos. Se vuelve a intentar solo la lectura desde el estado confirmado anterior.
- 401/403: error seguro de autenticación/permisos; sin cuerpo remoto ni excepción original. No hay renovación implícita de OAuth ni repetición de acciones del workflow.
- 410: cursor expirado, error explícito que exige desactivar/reactivar. La nueva línea base no reconstruye el intervalo que el proveedor dejó de conservar. No se descarta ni avanza el cursor silenciosamente. Este error se muestra a través del estado del trigger; el administrador debe resolverlo.
- JSON inválido, respuesta >4 MiB, página >100 elementos, cursores repetidos sin progreso, ausencia de cursor obligatorio o configuración inválida: error; el estado propuesto no debe confirmarse ni encolarse parcialmente.
- Graph: enlaces de continuación solo `https://graph.microsoft.com`, sin usuario, puerto, fragmento ni parámetros ajenos al delta; ruta exactamente igual al recurso solicitado. No sigue URLs arbitrarias, endpoints de otras unidades ni redirecciones. El cursor es opaco y se conserva cifrado; nunca se devuelve como `data`. Las nubes soberanas de Microsoft y reescrituras de ruta del proveedor quedan rechazadas de forma explícita y segura.
- Los datos de evento usan listas de campos permitidos y no contienen cabeceras de autenticación, tokens de página, enlaces firmados o respuestas HTTP completas. Si un campo de texto devuelve literalmente el bearer configurado, se sustituye por `[redactado]`. Pueden contener datos personales de negocio (correo, comentarios, respuestas de formularios o celdas): la política de conservación corresponde al almacenamiento central del historial.

Se evitan los registros remotos porque estos doce eventos usan lecturas oficiales: no se crean watches Forms/Pub/Sub, canales Drive/Calendar, suscripciones Graph ni streams X. Desactivar o eliminar el trigger cancela su programación local; no hay una suscripción remota que renovar o eliminar. Esto evita requisitos de un endpoint público para este grupo, aunque los triggers webhook de otros proveedores sí lo necesitan.

## Verificación y límites

La prueba aislada cubre las doce definiciones, rechazo de recepción pública, validación de credenciales/configuración, páginas, cursores, invariancia de filtros, cortes iniciales, IDs estables, actualizaciones y eliminaciones observables, reanudación desde estado serializable, exclusión de URLs/secretos, aislamiento del recurso Graph, límites de rango/respuesta, cuotas, errores HTTP/transporte y ausencia de reintentos con efectos. Estas son pruebas con Guzzle MockHandler y reloj fijo, sin red ni BD.

La atomicidad BD, reclamación concurrente, deduplicación entre procesos, encolado y ejecución real posterior pertenecen a las pruebas compartidas de infraestructura. No se han validado cuentas reales, scopes concedidos por un tenant, cuotas contratadas, cron desplegado ni entrega en una instalación real. Ninguna de esas acciones externas fue ejecutada por esta prueba.
