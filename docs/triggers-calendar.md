# Calendarios: evento próximo

`CalendarPollingProviders` implementa `microsoft_graph_event_upcoming` y `google_calendar_event_upcoming`, ambos `calendar.event.upcoming`. Se configuran `lead_minutes` (1–10080) y una credencial `generic_bearer` con access token OAuth vigente, plano o JSON `{"access_token":"TOKEN_FICTICIO"}`. No renueva OAuth ni crea suscripciones push.

Microsoft admite `token_mode=delegated` (predeterminado) o `application`; este último exige `user_id` y los consentimientos del tenant. `calendar_id` es opcional para usar el calendario predeterminado. Permisos mínimos oficiales: `Calendars.ReadBasic`, con alternativas `Calendars.Read`/`Calendars.ReadWrite` según acceso. `calendarView` devuelve ocurrencias recurrentes y excepciones, con paginación. Se solicita UTC y se restringen los enlaces al mismo origen y ruta. [Microsoft calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0).

Google requiere `calendar_id` (`primary` permitido), API Calendar habilitada, acceso al calendario y scope `calendar.events.readonly` o `calendar.readonly`. Se usa `events.list`, expansión de recurrencias y paginación por token con límites temporales invariables. Se filtra localmente por inicio porque el listado también incluye eventos que solapan el rango. [Google events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).

La primera lectura comprueba acceso con una ventana futura de un segundo y establece una marca silenciosa en la hora actual: no avisa del histórico desde activación. Después congela una ventana de vencimiento `[marca−2 segundos, ahora)` y consulta los inicios desplazados por la anticipación. El ID es hash del ID de ocurrencia y su inicio canónico UTC; una nueva hora de inicio permite un aviso distinto. La marca solo avanza tras completar las páginas, coordinada con el encolado duradero por el core.

Cada turno lee una página de hasta 100, con TLS, sin redirecciones, límite 4 MiB y timeouts 5/20 segundos. Los eventos de todo el día, cancelados o ya comenzados se omiten. El inicio y vencimiento se normalizan a segundos UTC; `data` incluye `id`, `summary`, `start`, `due_at`, `end` cuando exista, `lead_minutes`, `calendar_id` y serie cuando corresponda. No se entregan cuerpos, asistentes ni enlaces firmados.

Cron cada minuto, continuaciones, caídas y cuotas pueden retrasar avisos. Si el evento comenzó durante una interrupción, no se envía un recordatorio vencido. Creaciones o reprogramaciones con vencimiento anterior a la ventana ya confirmada pueden quedar fuera. El sondeo no es una alarma de tiempo real ni garantiza observar todas las revisiones. Cambiar configuración/token exige reactivar y establece una nueva línea base.

429/408/5xx o transporte fallido reprograman únicamente la lectura y respetan Retry-After. 401/403, formato inválido y cursores ajenos producen errores seguros. Los workflows y sus acciones no se reintentan aquí. Verificación: `php tests/triggers/calendar_polling.php` usa HTTP/reloj simulados; cubre baseline, ventanas, fronteras, recurrencia, paginación, reinicio, deduplicación de IDs, cambios de inicio, zona horaria, SSRF y fallos. No se usaron calendarios reales ni cron real. Estado: listo para configuración externa tras despliegue, credenciales y cron.
