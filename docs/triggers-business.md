# Triggers de servicios de negocio

Implementación: `src/Core/TriggerProviders/BusinessPollingProviders.php`. Prueba local reproducible: `php tests/triggers/business_polling.php`. Las pruebas usan Guzzle MockHandler, reloj y estado simulados; no consultan proveedores ni bases reales.

## Contrato y activación

Cada configuración vincula una clave estable del catálogo a un workflow y un nodo inicial. Las acciones existentes conservan sus identificadores. El adaptador produce `events[]` con `id`, `type`, `occurred_at` y `data` de metadatos seleccionados; nunca devuelve el cuerpo completo de las APIs. Para obtener contenido, usar posteriormente el nodo de acción correspondiente con el ID entregado.

La credencial seleccionada debe contener el JSON de secretos indicado por el catálogo en `generic_bearer.data.api_key`. Los tokens simples se normalizan centralmente a `access_token`/`api_key`. Nunca escribir tokens en configuración pública ni parámetros de nodos. Los campos `site_url`/`instance_url` de las credenciales usan HTTPS canónico, sin consultas, fragmentos, credenciales en URL ni redirecciones.

Los adaptadores están implementados y verificados con mocks. El estado operativo es **listo para configuración externa**, sujeto al despliegue, migración, credenciales válidas, activación del workflow y cron del coordinador. No se ha registrado ninguna suscripción remota.

## Polling: política común y garantías

- Primera ejecución: valida configuración y persiste `watermark=activated_at` sin leer ni emitir histórico. La segunda lee desde la activación, incluidos los eventos posteriores a ella mientras cron estuvo detenido.
- El estado está vinculado a tipo/configuración y contenido de credencial mediante hash. Cambiar el recurso o editar el token en la misma credencial rechaza cursores anteriores antes de llamar la API; pausar/reactivar establece otra línea base y no reconstruye el periodo perdido.
- Cada intento lee una página de hasta 100 registros. Se fija una ventana `[max(activated_at,watermark-300s), now-30s]` y se conserva hasta completar todas sus páginas. Los cursores opacos se pasan como parámetros, nunca se siguen URLs devueltas por el proveedor.
- `has_more` pide continuación al coordinador. `watermark` solo avanza cuando se completa la ventana. El estado y el encolado de eventos deben confirmarse en una transacción, bajo el bloqueo del coordinador; este adaptador no escribe a la BD.
- El solapamiento de cinco minutos recupera indexación tardía dentro de esa ventana. El ID estable incluye tipo, recurso y timestamp remoto; el almacén compartido deduplica por configuración. No se promete recuperar indexación demorada más de cinco minutos ni cambios intermedios entre lecturas de recursos mutables.
- HTTP 408, 429, 5xx y errores de transporte de **lectura** lanzan `TriggerRetryException`; `Retry-After` numérico o fecha se respeta y se acota a 1–86400 segundos. 401/403 y validación fallan con errores seguros. No se reintentan acciones externas desde este adaptador.
- La paginación de recursos mutables no es un snapshot transaccional del proveedor: cambios simultáneos pueden mover elementos; el solapamiento reduce ese riesgo pero no garantiza cada transición histórica. Si se requiere cada evento intermedio, elegir el webhook específico cuando esté implementado.

## Webhooks implementados en este adaptador

Antes de registrar externamente: desplegar callback HTTPS público del coordinador, guardar credencial, configurar el receptor para el workflow/nodo exacto, comprobar la migración y cron. Registrar **una sola suscripción por configuración**; conservar su ID y deshabilitarla/borrarla en el proveedor al pausar o eliminar la configuración local. La baja local impide ejecución aunque el proveedor siga enviando; no llama automáticamente la API de baja remota.

## HubSpot: eventos exactos por webhook

Además de los cuatro polling de estado, se implementan `hubspot_webhook_contact_created` (contact.creation), `hubspot_webhook_contact_property_changed` (contact.propertyChange), `hubspot_webhook_deal_created` (deal.creation) y `hubspot_webhook_deal_property_changed` (deal.propertyChange). El webhook sí conserva eventos individuales entregados de la propiedad suscrita; el polling de estado no se presenta como equivalente.

Configurar `portal_id` y `app_id`; los eventos propertyChange exigen además `property_name` interno. La credencial debe contener `client_secret` de la aplicación: un token privado de acciones no sirve para verificar firma. Suscribir y activar el evento en la app con `crm.objects.contacts.read` o `crm.objects.deals.read` y permisos de la cuenta. Algunas propiedades (num_unique_conversion_events y hs_lastmodifieddate) no admiten suscripción y se rechazan. Las apps legacy públicas gestionan suscripciones en sus ajustes o vía API; las privadas mediante ajustes UI; las apps basadas en proyectos siguen su configuración declarativa. El webhook journal v4 es un producto distinto sin targetUrl y no es este receptor.

Se exige `X-HubSpot-Signature-v3` Base64 HMAC-SHA256 sobre **método + URI canónica + cuerpo original + X-HubSpot-Request-Timestamp** con el client_secret; el timestamp está en milisegundos y se valida ±300000 ms. Solo se decodifica en URI el conjunto oficial `%3A/%2F/%3F/%40/%21/%24/%27/%28/%29/%2A/%2C/%3B`; no se usa decodificación general ni cabeceras Host/Forwarded no confiables para elegir el receptor. El coordinador entrega callback_url canónica de la configuración. No hay desafío URL de HubSpot equivalente al challenge LinkedIn/Slack; las pruebas POST necesitan firma válida. Los callbacks antiguos que únicamente proporcionen firma v1/v2 quedan rechazados: usar integración con firma v3 vigente.

Cada entrega es lista de hasta 100 eventos. Se valida `portalId` y `appId` firmados contra la configuración antes de producir eventos; se filtra subscriptionType/eventType y propertyName exacto. HubSpot no garantiza unicidad de eventId: se deduplica por hash de cuenta/app/objeto/tipo/propiedad/occurredAt/eventId/subscriptionId/valor, excluyendo attemptNumber para que un reintento no cree otra ejecución. El valor se utiliza únicamente dentro del hash; la salida contiene object_id, portal_id, app_id, event, property_name y occurred_at_ms, sin PII ni propertyValue.

**Configuración externa importante:** el target URL de HubSpot pertenece a la aplicación, no a cada suscripción. Este receptor enlaza inequívocamente un callback con una configuración: usar una app/configuración receptora dedicada para su evento/propiedad. No registrar sucesivamente callbacks distintos de la misma app suponiendo que coexistirán: el último reemplazaría al anterior. Este adaptador no ofrece fanout de una app hacia múltiples configuraciones/workflows. Al pausar o borrar localmente, desactivar la suscripción remota en HubSpot para detener reintentos. No se ejecutan cambios remotos desde P8P.

Fuentes: [validación v3 oficial](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/authentication/request-validation), [eventos, scopes, límite, targetUrl y eventId](https://developers.hubspot.com/docs/api-reference/legacy/webhooks/guide).

## Eventos y transportes no soportados

Estas limitaciones no se presentan como “listo para configuración externa”:

- **Notion polling frente a webhooks**: este adaptador polling no distingue cambios de propiedades y contenido. Los eventos exactos `page.created`, `page.properties_updated`, `page.content_updated` están implementados separadamente en el adaptador cloud con bootstrap cifrado pendiente y confirmación administrativa; consultar `triggers-notion.md`. No configurar ambos transportes sin considerar duplicación semántica entre eventos distintos. [Proceso oficial](https://developers.notion.com/reference/webhooks).
- **MySQL** cambios genéricos INSERT/UPDATE/DELETE: no existe un endpoint HTTP universal para detectar todos. CDC/binlog requiere permisos y consumidor adicional incompatibles con cron puro en hosting típico. Polling de tabla con PK y updated_at mantenido por la aplicación es viable para filas actuales, pero necesita contrato específico de tabla/columnas/tipos, no cubre DELETE ni estados intermedios y no equivale a CDC. El nodo existente solo ofrece acciones y no anuncia CDC. No hay adaptador ni SQL arbitrario añadido. [Actualización TIMESTAMP](https://dev.mysql.com/doc/refman/8.4/en/timestamp-initialization.html).
- **AWS S3** ObjectCreated/ObjectRemoved: S3 notifica a SNS/SQS/Lambda/EventBridge; no envía un webhook HTTP firmado propio directo. SQS se puede sondear desde PHP y es compatible con hosting si se configura cola/IAM, pero requiere receptor/transporte SQS, firma SigV4 y gestión confirm/delete del mensaje coordinada con encolado, ausentes en este adaptador. ListObjectsV2 puede observar claves actuales y ETag/LastModified, pero no recupera versiones intermedias/borradas ni equivale a ObjectCreated/ObjectRemoved. No se presenta esa aproximación como trigger. [Destinos/eventos](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html).
- **Discord Gateway completo**: WebSocket con heartbeats, intents y reanudación de sesión requiere proceso residente. Polling de mensajes creados es alternativa parcial explícita, no cubre edición/borrado/reacción. [Gateway](https://docs.discord.com/developers/events/gateway).

## Verificación y acciones externas

Aprobadas: sintaxis PHP; catálogo sin I/O; baseline de los 19 polling; emisión y filtrado de metadatos; IDs estables en solapamiento/reinicio; límites, cursores, ventana congelada; keyset Salesforce con empate de timestamps; rechazos de autenticación/transporte/cuota/JSON; firmas válidas y cuerpos alterados; replay temporal; audiencia/organización/receptor equivocados; challenge LinkedIn; POST verificación PayPal sin seguir cert_url remoto. Comando reproducible arriba.

No ejecutadas: APIs reales, permisos reales, registros/bajas/renovaciones en proveedores, BD y cron reales. No se instalaron dependencias ni se produjeron efectos remotos. Las verificaciones de almacenamiento, concurrencia, workflow desactivado y encolado/ejecución corresponden a las pruebas compartidas del coordinador.
